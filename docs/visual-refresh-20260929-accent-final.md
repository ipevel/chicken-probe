## 1. 决定一：主色 → 冷松绿 `#2f6b52`

### 1.1 定稿 token（亮 / 暗两套）

| token | 亮 | 暗 | 实测 |
|---|---|---|---|
| `--accent` | **`#2f6b52`** | **`#8ecdb3`** | 文字：白纸 **6.28:1** ✅ / 暗纸 **9.08:1** ✅ |
| `--accent-fill` | **`#2f6b52`** | **`#8ecdb3`** | 填充：白纸 **6.28:1** ✅（≥3:1）→ **与 `--accent` 合并为同一个值** |
| `--accent-soft` | **`#e0f0e9`** | **`#1b2b25`** | H154° / H158°，冷调淡绿；`--accent` 压上去 5.32:1 / 8.13:1 ✅ |
| `--accent-on-soft` | **`var(--accent)`** | **`var(--accent)`** | **独立取值取消**；压上去 5.32:1 / 8.13:1 已达标 |

### 1.2 结论一：`--accent` 与 `--accent-fill` **可以合并**（这是新主色的红利）

旧方案必须拆两个值，原因是原品牌绿太亮：`--accent-fill #6aa84f` 作文字只有 **2.87:1**，
所以文字位另设了压深过的 `#4a7a37`。新主色是深色，一个值同时满足两个阈值：

| 角色 | 阈值 | `#4a7a37`（旧 accent） | `#6aa84f`（旧 fill） | **`#2f6b52`（新）** |
|---|---|---|---|---|
| 文字 | ≥4.5:1 | 5.08:1 ✅ | 2.87:1 ❌ | **6.28:1 ✅** |
| 填充/描边 | ≥3:1 | 5.08:1 ✅ | 2.87:1 ❌ | **6.28:1 ✅** |

合并后对三个底面的实测（这正是团队要求的三处）：

| 底面 | `--accent` 同时作文字与填充 |
|---|---|
| `--paper` `#ffffff` | **6.28:1** ✅ |
| `--bg` `#f5f6f7` | **5.80:1** ✅ |
| `--surface-2` `#fafbfc` | **6.06:1** ✅ |
| `--accent-soft`（新）`#e0f0e9` | **5.32:1** ✅ |

> 顺带一个事实：当前 `var(--accent-fill)` 与 `var(--accent-on-soft)` **在 `theme/**` 与 `shared/**` 里都是零引用**
> （只在 `:18/:70/:75/:108` 出现定义与注释，`style.css:16` 的注释提到了 fill）。
> 也就是说这两个名字现在是**死声明** —— 合并不会破坏任何调用点。名字保留（`--accent-fill: var(--accent);` 或直接同值）
> 比删掉更安全：哪天要做浅色填充档，名字还在。

### 1.3 结论二：暗色档 = **同一枚色的提亮版**，不是另挑一个绿

亮 `#2f6b52` = H155° / S39% / L30.2%；暗 `#8ecdb3` = H155° / S38.7% / L68%。
**色相与饱和度不动，只把明度从 30.2% 提到 68%。** 这样暗色档不需要单独审美决策，也不会跑偏成另一个品牌色。

暗色档对三处底面的实测：`#1c1f24`(paper) **9.08:1** / `#22262c`(surface-2) **8.35:1** / `#14161a`(bg) **9.95:1**，全部 ✅。

### 1.4 结论三：`--accent-soft` 从偏黄的 `#eaf3e4` 退到冷调 `#e0f0e9`

| | 旧 `#eaf3e4` | 新 `#e0f0e9` |
|---|---|---|
| 色相 | H96°（黄绿，与主色 H103° 同族） | **H154°**（与主色 H155° 同族） |
| 饱和度 / 明度 | S38.5% / L92.4% | S34.8% / L91% |
| 与白纸的 ΔE | 9.8 | **9.4** |
| `--accent` 压上去 | 4.46:1 ❌（所以旧方案才有 `--accent-on-soft`） | **5.32:1** ✅ |

**为什么挑这个值**：`--accent-soft` 目前唯一的用途是 `.ghost:hover` 的悬停底（`style.css:199`）。
它要「看得出来变了、但不像选中」。旧值相对白纸的层次是 ΔE 9.8，我按这个视觉强度找同色相候选，
`#e0f0e9` 的 ΔE 是 9.4 —— **层次几乎没变，但色相从黄绿挪到了冷松绿一族**。
（对照：`--bg #f5f6f7` 相对白纸的 ΔE 只有 3.2，`--line-2 #d2d5da` 是 15.1。所以 9.4 落在「明显的浅色底、但不抢眼」这一档。）

### 2.1 `--c-down` 与 `--c-ping-4`：**本轮纳入（必须做）**（唯一一处「非 WCAG 阻塞」的变色）

这条不是为了让对比度达标，是为了**不打破这套调色板自己已经建立的色差纪律**。

现役折线两两 `ΔE`（都在同一张图里出现）：

| 一对 | ΔE |
|---|---|
| `--c-ping-3` ↔ `--c-ping-1` | **41.1**（最小的一对） |

| `--c-mem` ↔ `--c-disk` | 54.5 |
| `--c-cpu` ↔ `--c-up` | 60.3 |

| | 亮色 | 暗色 |

暗色档：`#5fc9b4` → **`#5cc2cf`**（ΔE 对暗主色 22.6、对暗 `--c-mem` 26.0、对暗纸 7.93:1）。

裁定结果与依据见 **§8.2 裁定二**，摘要两句：

1. **代价极低**：一次改 4 个值，不新增 token、不动任何选择器，与主色改动同批提交即可。
2. **这是本次改动引入的副作用，应当由本次销毁。** 新主色把面板品牌绿搬进了 `--c-down` 的色相邻域，

   就画在折线图上 —— 这不是审美问题，是「主色一进图表邻域，下行线就可能被读成主色」的**读数风险**。

> 若本轮真的要顺延：不改**不会**产生 WCAG 失败（3.92:1 达标），但下一轮必须补，
> 且要在 `--c-down` 那行留一句注释说明它和 `--accent` 的距离关系，

## 3. 决定三：3D 草地 / 天空 / 雾**不降调**

> 团队问的是：「面板主色与 3D 草地分属不同色相后，HUD 压在草地上会不会脏？」

### 3.1 结论

**不会脏 —— 而且这不是「不会」，是「不可能」。** 三条依据，全部可核。

同时明确：**草地 `#9fd08a`、天空 `#a8d8f0`、雾、`theme-color`、favicon 图块，一个都不降调。**
但「面板主色与草地刻意同源」这条旧约束**要重写**，见 §3.4。

### 3.2 依据一：鸡场 CSS 里 `var(--accent)` 的引用数是 **0**

这不是印象，是结构事实。

`--accent` 在 `theme/style.css` 里的全部引用点：

| 行 | 选择器 / 上下文 | 属于 |
|---|---|---|
| `:72` | `:root { --focus: … var(--accent) }` | 面板 |
| `:128` | `html.dark { --accent-on-soft: var(--accent) }` | 面板 token |
| `:177` | `@supports not selector(:focus-visible)` → `button:focus, a:focus, input:focus, select:focus` | 面板 |
| `:199` | `.ghost:hover { background: var(--accent-soft) }` ← **是 `--accent-soft`，不是 `--accent` 本体** | 面板 |
| `:215` | `.conn.live`（`color` + `color-mix` 混色基底，同一行两处） | 面板 |
| `:349` | `.mid .k b.live` | 面板 |
| `:386` | `.spark path` | 面板详情抽屉 |
| `:421` | `.chart .live-dot` | 面板详情抽屉 |

> 计数口径（供苏小测直接 grep）：`grep -n -e 'var(--accent)'` 命中 **7 行**（`:72 :128 :177 :215 :349 :386 :421`），
> `grep -n -e 'var(--accent-soft)'` 命中 **1 行**（`:199`）。**8 行全部 < 441**，鸡场区块内一行都没有。

> **行号与条数已漂（2026-09-29 补注）**：上面这组数字是 delta 套用**之前**的快照。
> 套用完成后区块头在 `:453`、文件 763 行；`var(--accent)` 命中 **10 行**、`var(--accent-soft)` **1 行**（共 11 处）。
> 多出来的是 delta 自己引入的别名声明（`--accent-fill: var(--accent)` / `--accent-on-soft: var(--accent)` 之类）。
> **本节结论不变**（窗口内仍为 0），但**别再用「7 行 / 8 行 / `:441`」这些数字去核对** ——
> 核对的权威形式已挪到 **§7.3 ①**：按区块头**锚点**取窗口，只判「窗口内计数 = 0」，不写行号、不写条数。

而鸡场区块从 **`style.css:441`** 开始（区块头 `/* ---------------- 鸡场 ---------------- */` 在 `:441`），
**一直到文件末尾**（`:749`，含其后的响应式与 `prefers-contrast` / `forced-colors` 媒体查询）。
在这 **309 行**里搜 `--accent`：**结果为空**。

**8 个引用点全部 < 441，零个落在鸡场区块内**（连它后面的媒体查询也没有）。鸡场侧只用 `--farm-*` 一族。
所以把 `--accent` 从 `#4a7a37` 换成 `#2f6b52`，**鸡场渲染在结构上就不可能有任何变化** —— 不是观感差异小，是同一个字节都没有。

> 渲染核对：`docs/icons-preview.html` 的 ②b 节放了两块**同一份 HUD、分别声明 `--accent: #4a7a37` 与 `--accent: #2f6b52`** 的草地卡片，
> 并排看完全一致。这就是上面结论的直观证据。

### 3.3 依据二：明度上的物理约束 —— 任何压深的品牌绿都进不了鸡场

就算是「假设有人非要把主色画进 HUD」，也算不出一个可用的结果：

HUD 文字的实际底色不是草地本身，而是**玻璃叠草地**的合成色：
`over(rgba(18,28,14,.62), #9fd08a)` = **`#48603d`**。

| 文字色 | 压在 `#48603d` 上 |
|---|---|
| `--farm-good #c0eb96`（现役） | **5.16:1** ✅ |
| 新主色 `#2f6b52` | **1.11:1** ❌ |
| 暗色主色 `#8ecdb3`（已经是「提亮版」） | **3.82:1** ❌ 仍不达标 |
| `--farm-ink #ffffff` | **6.96:1** ✅ |

> **交叉验证（这条能证明上面的合成色没算错）**：`over(rgba(18,28,14,.62), #9fd08a)` 用 `Math.round` 逐通道合成，
> 得 `#48603d`；而 `theme/style.css:91` 里 `--farm-good` 那行**原本就写着** `/* 4.76:1 / 5.16:1 联机中 */` ——
> 我算出的 5.16 与它**逐位吻合**（4.76 是同一个色压在 `over(…, #a8d8f0)` = `#4b6364` 天空底上的值）。
> 两个独立来源对上，说明 `#48603d` 是对的。

**结论：鸡场文字必须留在「高亮度」这一档。这是明度约束，不是色相问题。**
所以「草地要不要跟着主色降调」这个问题本身问错了方向 ——
真正把两者分开的是**亮度**，不是色相。品牌绿再换多少种，都进不了这块深色玻璃。

### 3.4 依据三：「刻意同源」这条约束要重写，但**不是靠压草地的明度来实现**

先把事实摆清：

| | 色相 | 与草地的 ΔE |
|---|---|---|
| 草地 `#9fd08a` | H102°/S42.7%/L67.8% | — |
| 旧 `--accent` `#4a7a37` | H103° | **32.2**（同族） |
| 旧 `--accent-fill` `#6aa84f` | H102° | 39.8 |
| 旧 `--accent-soft` `#eaf3e4` | H96° | — |
| **新 `--accent` `#2f6b52`** | **H155°** | **43.7**（明显不同族） |

旧的亮色三元组（`#4a7a37` / `#6aa84f` / `#eaf3e4`，H96–103°）与草地 H102° 确实是一个色相家族，
这不是巧合。改完之后这条链断了。**我判定：接受它断，不靠压草地来续。**

理由三条：

1. **草地的身份是「阳光下的草」，不是品牌色。** 草地的黄绿（H102°）是自然物固有色。把它拉向 H155° 的松绿，
   会读成湿地苔藓 / 阴影里的草，与这个场景设定（白天、晴、有太阳方向光）直接冲突。
2. **局部降调会露色相断层。** `world.js:139-141` 的 `scene.background` 与 `scene.fog` 是**刻意同值**的 `SKY = 0xa8d8f0`；
   要动草地就得连雾和背景一起动，否则远山与地平线接缝处会出现色相跳变。再往下，`world.js:145-148` 的
   `HemisphereLight(0xcfe6ff, 0x8a9a5a, 0.95)` 与 `DirectionalLight(0xfff2d8, 1.6)` 是按这套地表色配的。
   **动一轮草地 = 重做一遍场景光照**，代价与收益完全不成比例。
3. **`--farm-grass` 的角色是「场景兜底色」，不是「界面色」。** 它同时被
   `.farm { background }` 与 `body.in-farm { background }` 使用（`style.css:446, 452`），
   用于 iOS 回弹时露出的底色 —— 它**必须与 3D 草地视觉接得上**。所以它跟场景走，不跟主色走。

**正确的做法是把「同源」从「色相相同」改成「分工明确」**，并且落成注释纪律：

| 色系 | 成员 | 归属 | 纪律 |
|---|---|---|---|
| **面板品牌绿** | `--accent` `--accent-fill` `--accent-soft` `--accent-on-soft` `--focus` | 面板（`style.css` ≤ `:420`） | H155° 松绿。可以换色相，但必须整族一起动 |
| **场景自然绿** | `--farm-grass` + `world.js` 的地表/植被材质 | 鸡场（`style.css` ≥ `:441`） | H90–102° 黄绿。**不跟随品牌色**，因为它是自然物固有色 |
| **状态绿（必须压在深色玻璃上）** | `--farm-good` `--hpfill` `.tc-btn.on` | 鸡场 HUD | 高亮度档（≥ `#c0eb96` 的亮度）。**不跟随品牌色**，因为明度约束（§3.3） |

**这套分工要写进注释**，否则下一个人看到「面板松绿、草地黄绿」会以为是没统一。

### 3.5 `theme-color` 与 favicon 图块：**不降调**，而且有硬依据

这两处是唯一可能「两个绿同屏」的地方（移动端：浏览器标签栏/地址栏是 `theme-color`，页面内容是面板主色），
所以必须单独给结论。

**结论：都不改。** 硬依据是 favicon 的**图块与鸡头的对比度**：

| 图块色 | 鸡头 `rgb(30,58,22)` = `#1e3a16` 压上去 |
|---|---|
| 现役 `#9fd08a` | **7.10:1** ✅ |
| 松绿 `#2f6b52` | **2.00:1** ❌ 鸡看不见了 |
| 中调 `#5c9d7d` | 3.93:1 ⚠ 只剩图形级 |
| 亮松绿 `#8ecdb3`（暗色主色档） | 7.07:1 ✅ |

鸡头是**深绿实心**，图块一旦压深到松绿，两者明度就贴在一起了。
所以 favicon 图块要跟主色走，**必须同时把鸡头改成浅色**（例如 `#d8f0c8`）—— 那是另一次改动，不是「顺手换个色」。

而 `theme-color #9fd08a` 与 favicon 图块**是同一个 hex**，它们构成「图标 + 标签栏」**这一个识别面**，
必须同进同退。现状两者一致，是正确状态；只改一个会造成图标与标签栏脱节。

**记录一个将来的选项**：真要让 favicon 走品牌色，正确做法是
图块用 `#8ecdb3`（亮松绿，7.07:1 ✅）+ 鸡头保留深绿。那时 `theme-color` 一起换成 `#8ecdb3`。
这个组合对比度是够的，只是本轮未获授权，不改。

## 4. 决定二：控件边界提到 WCAG 3:1

### 4.1 团队给的两个候选值有一个不达标，需要微调

| 候选 | 对 `--paper #ffffff` | 对 `--bg #f5f6f7` | 对 `--surface-2 #fafbfc` |
|---|---|---|---|
| 亮 `#8b9098`（团队给的） | 3.21:1 ✅ | **2.97:1 ❌** | 3.10:1 ✅ |
| **亮 `#858b93`（定稿）** | **3.44:1** ✅ | **3.18:1** ✅ | **3.32:1** ✅ |
| 暗 `#69707a`（团队给的） | 3.30:1 ✅ | 3.62:1 ✅ | **3.04:1**（余量太薄） |
| **暗 `#6f767f`（定稿）** | **3.60:1** ✅ | **3.94:1** ✅ | **3.31:1** ✅ |

**为什么亮色要往下压一点**：边界同时邻接「控件内填色 `--paper`」和「页面底 `--bg`」两个色，
**对比度要取更差的那个**。`--bg #f5f6f7` 比白纸暗，所以对它是更严的一侧。
`.controls` / `.tabs` / `.ranges` 里的控件正是直接坐在 `--bg` 上，`#8b9098` 在那上面只有 2.97:1 —— **差一点点不达标**。

**为什么暗色要往上提一点**：`--surface-2 #22262c` 比 `--paper #1c1f24` 亮，是更严的一侧。
`#69707a` 贴到 3.04:1，余量只有 0.04；`#6f767f` 留到 3.31。

### 4.2 token 拆分策略：`--line` / `--line-2` / `--line-control` / `--line-control-hover`

现状问题是 `--line` 与 `--line-2` **同时承担「分隔线」和「控件边界」两种语义**。
拆法如下（**不是**改 `--line` 或 `--line-2` 的取值，而是把它们的使用范围收窄）：

| token | 职责（收窄后） | 取值 | 判据 |
|---|---|---|---|
| `--line` | **分隔线 / 轨道 / 网格线**：`border-top`、`border-bottom`、`.chart .grid`、`.spark .axis`、`.bar`（`:335`）与 `.seg`（`:324`）的轨道 | 亮 `#e5e7ea`（1.24:1）/ 暗 `#2a2e35`（1.21:1） | **不变**。分隔线不适用 1.4.11 的 3:1；提到 3:1 会让整页变成表格线 |
| `--line-2` | **强调线**：国旗外环、`.flag-text` 边框、`.chart-readout` 边框、`.seg.dim > i.on`（`:333`） | 亮 `#d2d5da`（1.47:1）/ 暗 `#383d45`（1.51:1） | **不变**。它服务的是「容器层次」，不是可交互边界；改了会连带 `.seg.dim` 的语义 |
| **`--line-control`** | **可交互控件的常驻边界** | **亮 `#858b93`（3.18:1 对 `--bg`）/ 暗 `#6f767f`（3.31:1 对 `--surface-2`）** | 新增独立取值，**不再等于 `--line-2`** |
| **`--line-control-hover`** | **同上，悬停态** | **`var(--ink-3)`** → 亮 `#6b7178`（4.93:1）/ 暗 `#8d949e`（5.40:1） | 新增。见 §4.3 —— 不加这个会出方向错误 |

**「哪个算控件」的判定规则**（要写进注释，否则以后又会混）：

> **边框内就是点击目标、且内容不足以独立表明「这里可点」的 → `--line-control`。**
> **边框内是只读内容、或整块内容本身表明可点的 → `--line`。**

按这条规则落位：

| 归 `--line-control`（控件） | 归 `--line`（容器 / 展示） |
|---|---|
| `.ghost`（按钮）、`.chip`（可点筛选片）、`.viewtoggle button`、`.tab`、`.range`、`.controls select`、`.controls input[type=search]` | `.card`、`.summary .cell`、`.sstat`、`.drawer`、`.conn`（状态徽章）、`.pill`（状态徽章）、`.seg > i`（轨道） |

**`.card` 与 `.cell.clickable` 是这条规则下的边界情况**，归到 `--line`：
它们是整块内容即点击目标的容器，可点性由 `cursor:pointer` + 内容 + 阴影共同表达，边框不是唯一识别手段
（1.4.11 管的是「识别组件所必需的视觉信息」，这里边框不是唯一依据）。
**这一条已裁定：不提** —— 完整口径与可逆性见 **§8.2 裁定一**。若将来从严，把 `:270` 的 `.card` 与 `:221` 的 `.cell`
也换成 `--line-control` 即可（**一个 token 的改动、零新增色**），代价是整页 12 张卡片出现一道 3.4:1 的灰边。
**本方案按宽松解释处理，并在注释里标注。**

### 4.3 必须一起改的坑：`--line-2` 会把 hover 弄反

这是拆分时最容易漏的一处。现在有 **5 处** `border-color: var(--line-2);`（`style.css:199, 228, 238, 274, 399`），
它们全是 `:hover`。控件常驻边界一旦从 1.47:1 变成 3.18:1，而 hover 仍然切到 `--line-2`：

| 状态 | `--line`（旧常驻） | `--line-control`（新常驻） | `--line-2`（现 hover） |
|---|---|---|---|
| 亮色 | 1.24:1 | **3.18:1** | **1.47:1** ← 悬停后**变淡**了 |
| 暗色 | 1.21:1 | **3.60:1** | **1.51:1** ← 同样反向 |

**所以控件的 hover 必须换成 `--line-control-hover`。** 用 `var(--ink-3)` 的妙处是：它亮暗两套的取值方向天然相反
（亮 `#6b7178` 更深、暗 `#8d949e` 更浅），**两套主题下都表示「对比更强」**，不需要写两套规则。

对照：`.card:hover` 与 `.cell.clickable:hover` 的常驻边界仍是 `--line`（1.24:1），hover 切到 `--line-2`（1.47:1）
方向是对的，**不改**。

### 4.5 `.seg > i` 空槽：**明确不提对比度**（这条要给专门结论）

团队专门问了这一格，因为它「是数得出来的格子」。**我的判定是不提，而且提了会把机制改坏。**

空槽（未点亮的格）用的是 `var(--line)`（`style.css:322-325` 里的 `:324`），点亮格用 `--m-*`。判定要看的是**这两者之间的分辨率**：

| 空槽取值 | 对 `--m-cpu` | 对 `--m-mem` | 对 `--m-disk` | 对 `--m-load` | 对 `--warn-fill` | 对 `--danger-fill` | 最差 |
|---|---|---|---|---|---|---|---|
| **`#e5e7ea`（现役 `--line`）** | **3.45:1** | 4.83 | 3.73 | 3.97 | 2.14 | 3.66 | **2.14** |
| `#d2d5da`（`--line-2`） | 2.90 | 4.06 | 3.14 | 3.34 | 1.80 | 3.09 | 1.80 ❌ |
| `#b9bdc3`（高对比档的 `--line`） | 2.26 | 3.17 | 2.45 | 2.60 | 1.41 | 2.41 | 1.41 ❌ |
| `#8b9098`（团队给的边界候选） | 1.33 | 1.86 | 1.44 | 1.53 | 1.21 | 1.41 | 1.21 ❌ |
| `#858b93`（定稿边界） | **1.24** | 1.74 | 1.34 | 1.43 | 1.29 | 1.32 | 1.24 ❌ |

**结论三条：**

1. **现役 `#e5e7ea` 已经是这个家族里唯一能满足「点亮 / 未点亮」3:1 的值**（对 `--m-cpu` 3.45:1）。
   把空槽往「可见」方向提亮，只会把「这格亮没亮」的分辨率从 3.45:1 一路压到 1.21–1.86:1 —— **直接毁掉可数性**。
2. **提亮空槽还会引入第三种非指标色。** 现在的规则是「颜色只表指标身份，越线才切 warn/danger」
   （`style.css:38-41` 的注释写明了这条，最新快照为 `:38-41`）。空槽之所以可以那么淡，正是因为它**不参与颜色语义**。
   把它提到 3:1，16 格里就出现一条明显的中灰轨道，读者会开始猜「这条灰是不是也是某个指标」。
3. **它不是控件边界。** 空槽既不接受交互，也不是「信息本体」；信息由**已点亮的格数**与旁边的数字承担。
   1.4.11 约束的是「识别组件与状态所必需的视觉信息」，已点亮格本身就是那个信息。

> **替代手段（如果 QA 或用户坚持空槽要可见）**：不要提亮 `--line`，而是给每一格加 1px 的
> `outline: 1px solid var(--line-control)`、格内保持透明 —— 让**可数性来自边界而不是颜色**，
> 不引入第三色。代价是计量条会变成带网格的样子。这是备选，不是建议。

#### ① 结构断言：鸡场区块内 `var(--accent)` 引用数为 **0**

鸡场区块从 `theme/style.css` 里那行区块头 `/* ---------------- 鸡场 ---------------- */` 开始，
一直到文件末尾 —— 取「区块头 → 末尾」这个窗口，比只取鸡场规则本身**更严**
（把它后面的媒体查询也一起管住）。

**本小节的命令已改为「按区块头锚点取窗口」**，不再写死行号：

```bash
# 在项目根目录执行；期望输出 0（grep 无匹配时退出码为 1，这是「通过」不是「失败」）
awk '/^\/\* -+ 鸡场 -+ \*\//{f=1} f' theme/style.css | grep -c -e '--accent'
```

> **为什么不写行号**：这道断言里行号会漂。写这份文档时区块头在 `:441`，苏小码套用主色 delta
> 之后它在 `:453`（文件 763 行）；`NR>=441` 与锚点式取窗的结果**虽然都是 0**，但前者此时
> 多吃了 12 行上一区块的内容，窗口已经名不副实。锚点式不会漂。
> （行号的权威口径见 §0.1：**行号只是提示，锚点是原文**。）

再确认**所有**引用点都落在窗口**之前** —— 同样不写死条数：

```bash
# 两个名字都查。期望**两条都是 0**（即：窗口内一处引用都没有）
awk '/^\/\* -+ 鸡场 -+ \*\//{f=1} f' theme/style.css | grep -c -e 'var(--accent)'
awk '/^\/\* -+ 鸡场 -+ \*\//{f=1} f' theme/style.css | grep -c -e 'var(--accent-soft)'
```

> 早先这里写的是「期望 7 行：`:72 :128 :177 :215 :349 :386 :421`」+「期望 1 行：`:199`」。
> 那是**写死了条数与行号**，套用 delta 后两边都漂了：截至 2026-09-29，
> `var(--accent)` 在全文件有 **10 行**、`var(--accent-soft)` 有 **1 行**（共 11 处），
> 但**全部 < 区块头所在行** —— 断言成立，只是「7 行」这个数字不能再用。
> 所以上面改成「窗口内计数 = 0」的形式：它等价、更严，而且**不随引用点增减而失效**。

#### ② 合成色断言：HUD 在草地上的实际底色必须是 `#48603d`（亮）/ `#3b5032`（暗）

HUD 文字真正压的底不是草地本身，而是「`--farm-haze` 半透明玻璃叠在草地上」的**合成色**。
直接在项目根目录跑这段（无依赖）：

```js
const hex = h => h.replace('#','').match(/../g).map(x => parseInt(x,16));
const over = (rgba, bg) => {
  const [r,g,b,a] = rgba.match(/[\d.]+/g).map(Number);
  return '#' + [r,g,b].map((v,i) => Math.round(v*a + hex(bg)[i]*(1-a)))
    .map(v => v.toString(16).padStart(2,'0')).join('');
};
over('rgba(18,28,14,.62)', '#9fd08a');   // 亮色：期望严格等于 '#48603d'
over('rgba(12,20,9,.68)',  '#9fd08a');   // 暗色：期望严格等于 '#3b5032'（html.dark .farm 覆写了 --farm-haze）
```

主色改动**前后各跑一次，两个值都必须严格相等**。这条断言一次守住三件事：
`--farm-haze` 没被顺手改、暗色档的 `--farm-haze` 没被顺手改、`--farm-grass` 没被顺手改。

> 与 `theme/style.css:91` 里 `--farm-good` 那行原本就写着的 `/* 4.76:1 / 5.16:1 联机中 */` 逐位吻合。
> 如果断言里的合成值算错了，这一步会立刻对不上，不会悄悄放过。

#### ③ 渲染断言（权威）：`.farm` 子树的计算样式指纹**不变**

**先说被废弃的那一版。** 本小节原写「改主色**前/后**进鸡场截图，`.farm` 区域**像素差 = 0**」。
这条**不可执行** —— 鸡场是**活场景**：NPC 在走、相机在动、云在飘，两次截图之间本来就有像素差。
「期望差异为 0」会被场景噪声直接吃掉，**必然误报**，且与主色改没改无关
（苏小码实测反驳成立）。所以它**降级为人眼旁证**（见本节末），**不再作为判据**。

**权威判据 = `.farm` 整棵子树的「计算样式」sha256 指纹。** 比像素差更严，而且完全确定性：

| | 像素差（已废） | 计算样式指纹（现行） |
|---|---|---|
| 确定性 | 否 —— 活场景下**必然非 0** | **是** —— 同一状态必得同一哈希 |
| 覆盖面 | 只看得到画出来的像素 | 逐元素逐项：**28** 个渲染属性 + **12** 个 `--farm-*` token |
| 定位能力 | 只说「有差异」 | 说**第 N 项、哪一项**不同 |
| 能否独立复跑 | 要人看图判 | **一条命令 + 一个哈希** |

实现：`.shots/farm-fingerprint.mjs`（苏小码）。逐元素导出计算值，取 `sha256(rows.join('\n'))`。

> **可复跑性的一个前提**：`.shots/` 在 `.gitignore` 里 —— 这个脚本与基线 JSON **都是本地资产、不进版本库**。
> 换一台机器复跑前要先把脚本与 `.shots/farm-fingerprint.json` 拿过来，否则 ①②③ 三条都跑不了。
> （本文档与 `docs/hud-top-probe.mjs` 在 `docs/` 下，**是**进库的。）

##### 怎么跑

```bash
cd <项目根目录>          # 需要 dev server：node server/dev.js（7788）+ 一个调试 Chrome（默认 9222）

# ①【权威】同 DOM A/B：先采「套了冷松绿」的，再在**同一份 DOM**上注入旧主色采一次。
#    两侧哈希必须**相等**，退出码 0。它**不依赖任何基线文件**，也不含场景抖动。
node .shots/farm-fingerprint.mjs --ab-old-accent

# ②【防回归闸门】与已记录的基线比对；不一致退出码 1。
node .shots/farm-fingerprint.mjs --check

# ③【换端复跑，可选】另一个 Chrome 端口、同一把尺子（只读，不写基线文件）
CDP=http://127.0.0.1:9333 node docs/hud-top-probe.mjs --fp --fp-check=.shots/farm-fingerprint.json
```

> **退出码有三档，别把 2 当成失败**：`0` = 指纹一致 / `1` = 指纹**真的**不同 /
> `2` = **采样未收敛**（连采 8 次哈希都不一致 —— 判据暂不可用，先让页面稳定再重跑）。
> 一个会自己误报的判据比没有判据更坏，所以必须把「渲染真的变了」和「页面还没稳定」分开报。

> **为什么把 A/B 排在 `--check` 前面**：`--check` 的证明力依赖「基线是在被检改动**之前**采的」，
> 而这一点**无法从基线文件本身看出来**。A/B 是同一会话内、元素集合完全相同的前后对比，
> 不依赖基线时点 —— 所以它才是**唯一**能直接回答「换主色有没有动鸡场」的那条。
> A/B 还会打印被换掉的全局 token（新旧 `--accent` 取值），能自证**不是空转**。

##### 本次实测（2026-09-29，两个 Chrome 实例）

- `.farm` 稳定元素数：**65**（数据驱动容器的后代已排除：`#board-rows` / `#feed`）
- 计算样式指纹：`56e86928bfa8c5c8b9bfa799f36a60493f636d7ed07c61e6ee53ce52d20b8a89`
- **`--ab-old-accent`：两侧同为该值，退出码 `0`**；同时打印出 `--accent` 由 `#4a7a37` → `#2f6b52`（确非空转）
- **`--check`：与 `.shots/farm-fingerprint.json` 一致，退出码 `0`**
- 可重复性：连跑 **3** 次、跨 **2** 个实例（9222 / 9333）同值；期间 `#board-rows` / `#feed`
  的后代数还在变（2 → 1 → 2 ……）**不影响哈希** —— 那正是排除它们的意义。

> **数字口径提示**：基线哈希以 **`.shots/farm-fingerprint.json` 当前记录为准**
> （`56e86928…`，采于 `2026-09-29T04:43:56Z`）。早先口头转述过的 `a5dc59b6…` / **71** 个元素
> 对应这个脚本的**更早一版**（那时还没把 `#board-rows` / `#feed` 的**后代**排除、
> 也还没把 `left/top/right/bottom` 从哈希里拆出去）。**两者不是同一个判据，别混着比** ——
> 混比会得到「指纹不同」，而那是脚本版本差异，不是回归。
> 复跑时以脚本**当次打印的**元素数与哈希为准；元素数对不上就先查脚本版本，不要先怀疑鸡场。

##### 这份指纹**不吃**什么（先知道，免得把噪声当回归）

1. **不吃数据驱动的后代**：`#board-rows`（榜名单）与 `#feed`（事件流）的**后代不进指纹**，
   只保留容器自身；行数另行打印。理由：行数随在线人数变，算进去会得到「65 → 79 个元素」这种假警报。
2. **不吃布局几何**：`left/top/right/bottom` 单独采、**不进哈希**。理由：绝对定位盒的 `right/bottom`
   是由「定位偏移 + 盒自身尺寸」推出来的，而盒尺寸由内容决定 —— 实测 `#board` 的 `bottom` 会随榜名单
   行数在 `798.312px` / `776.219px` 之间跳。与第 1 条是同一个失效家族。
3. **不吃全局 token 的取值**：`--accent*` / `--line-control*` / `--focus` / `--c-*` 不进哈希，
   只打印供核对。理由：A/B 的做法**就是故意去改这些值**，算进哈希等于自己制造差异；
   而「全局 token 变了」不等于「鸡场渲染变了」—— 只有它**落到某个元素的计算值上**才算。
   反过来这也更严：任何真的漏进鸡场的改动，**必然**在某个元素的计算样式上现形。

##### 覆盖边界（重要：别把「判据偏严」当成误报）

指纹跑在 **1440×900**，且覆盖 `#farm` **整棵子树** —— 而 **`#hud` 就在 `#farm` 里面**
（`theme/index.html:271` 的 `#farm` 包着 `:275` 的 `#hud`）。所以：

- **面板侧（`#hud-top` / `#board` / `#room-state` / `#feed` …）的计算样式也在指纹里**，
  实测差异定位能直接落到 `span#room-state.conn.live` 这一级。
- 若之后**有意**改面板侧（例如第 9 步把 `.conn.live` 的混色基底换成 `--line-control`），
  **指纹会跟着变** —— 那是**有意改动**、不是「主色漏进鸡场」，但闸门会照样报 `1`。
  **这种情况先重新采基线，并在提交说明里写清是有意改动**；不要靠放宽判据绕过。
- 反过来：**别的视口尺寸不要拿来比哈希**。视口一变，窄屏媒体查询会改 `#board` / `#hud-top`
  的计算样式，差异会被记到这份指纹上。**1440×900 是口径的一部分，不是随手选的。**

##### 判据自身的一个坑（我踩过，写下来免得下一个人再踩）

「从带模板字面量的脚本里正则取出表达式、再**原样**送进页面」是错的：
`.shots/farm-fingerprint.mjs` 里写着 `split(/\\s+/)`（模板字面量语义下 `\\s` 表示「反斜杠 + s」，
求值后才是正则 `/\s+/`）。照抄原文送进 `Runtime.evaluate`，页面拿到的是 `/\\s+/`
—— 匹配「一个或多个反斜杠」，于是元素键从 `span#room-state.conn.live` 变成 `span#room-state.conn live`，
**指纹必然不同**，判据当场变成一张假警报。取表达式必须**按模板字面量语义还原**。
`docs/hud-top-probe.mjs --fp` 已按此实现，并在注释里写明。

##### 三条断言各自守什么

| 断言 | 守什么 | 失效说明什么 |
|---|---|---|
| ① 窗口内引用数 = 0 | 主色**没有在鸡场区块里被引用** | delta 改到了不该改的地方 |
| ② 合成色严格相等 | `--farm-haze` / `--farm-grass` / 暗色档**没被顺手改** | 顺手改了鸡场自己的 token |
| ③ 子树指纹不变 | 前两条成立的前提下，鸡场**渲染结果**确实一点没变 | 有引用以**间接**方式漏了进来 |

③ 之所以必要：① ② 查的是**声明的文本**，③ 查的是**渲染出来的计算值** ——
只有 ③ 是「结果层」的断言，而 A/B 让它**不依赖任何历史文件**。

## 8. 缺口与已裁定的取舍

### 8.1 本轮没有验证的部分

1. **没有跑过真实 `theme/` 代码做「观感」判断 —— 但「鸡场没被改动」这一条已经在真实页面上验证过了。**
   设计结论（token 取值、对比度、ΔE）仍来自 `theme/style.css` 的静态阅读 + 色度学实算 +
   `docs/icons-preview.html` 的渲染；苏小码并发修改中，我读的是 §0.1 那组 md5 的快照。
   **例外是 §7.3 ③**：它在**真实页面**上跑过 —— 1440×900、`#farm` 全子树 65 个稳定元素、
   同 DOM A/B 两侧同哈希、退出码 `0`（实测段见 §7.3）。所以「换主色没动鸡场」**不是推理结论，是实测结论**；
   仍然缺的是**观感层**的判断：「新主色好看吗、暗色下够不够亮」这类问题没有渲染验证过。
2. **没有渲染验证 `.card` / `.cell` 提到 3:1 的样子** —— 因为**已裁定不提**（§8.2 裁定一）。
   这条因此不再是待办，只是一个存量缺口：将来若要从严（一个 token 的改动），**观感需先渲染确认**。
3. **`--c-down` 的改动没有渲染验证。** `#2e93a2` 是按 ΔE 算出来的平衡点（对主色 29.0、对 `--c-mem` 27.6），
   但「29 够不够分得开」要看真实图表里 1.6px 的线宽。**已裁定本轮必须改**（§8.2 裁定二），
   所以这条缺口转为**落地后的复核项**：改完在详情抽屉里并排看 `.chart .live-dot` 与「下行」折线。
   若仍难分辨，下一轮把 `#2e93a2` 再往青推一档（`#2e9aab`，ΔE 31.4 —— 但对白纸降到 3.32:1，这是要付的代价）。
4. **没有实测真机 favicon**（标签栏渲染尺寸与颜色管理可能有差异）。2.00:1 的结论是色度学计算，不是目视。
5. **`--line-control` 在 `.drawer` 里的表现没核**：抽屉底色是 `--paper`，但抽屉有 `box-shadow` 叠加，
   边界观感与页面上的按钮可能不同。

### 8.2 **已裁定的两个取舍**

这两项原本是「需用户知情」的开放取舍，**现已由团队裁定，不再需要用户决定**（用户已两次授权「按 AI 建议」）。
下面逐项写裁定结果与依据。

#### 裁定一：容器卡（`.card` / `.summary .cell`）**不提** 3:1 —— 保持 `var(--line)`

**口径（建议原样写进 `theme/style.css` 的注释，避免以后被当成「双标」改回去）：**

> **WCAG 1.4.11 管的是「识别组件所必需的视觉信息」。**
> `.card` / `.summary .cell` 的可点性由「整块填充面 + 阴影 + 内容本身 + `cursor:pointer`」共同表达，
> 边界线圈**不是**识别它的唯一依据；
> 而控件（`.ghost` / `.chip` / `select` / `input[type=search]` / `.tab` / `.range` / `.viewtoggle button`）
> **内部就是点击目标、内容不足以独立表明「这里可点」**，所以边界必须达标。
> 两者适用**同一条规则**，只是**判定结果不同** —— **不是双标。**

**可逆性（这条决定了「不提」是一个低风险决定）：**

> 容器卡现在用的是 `var(--line)`。将来若要从严，把 `.card`（`:270`）与 `.summary .cell`（`:221`）的边框
> 换成 `var(--line-control)` 即可 —— **一个 token 的改动、零新增色**。
> 不需要重新设计、不需要新增变量；代价只是整页 12 张卡片出现一道 3.4:1 的灰边（与「值班扫读」目标冲突）。

严格版做法见 §4.2 末段。本文档的 **B 表不含** `.card` / `.cell` 两行 —— 这是有意为之，不是遗漏。

#### 裁定二：`--c-down` / `--c-ping-4` —— **本轮就改**（亮 2 值 + 暗 2 值，共 4 处）

| token | 亮 | 暗 |
|---|---|---|
| `--c-down` | `#2f8f7f` → **`#2e93a2`**（`style.css:33`） | `#5fc9b4` → **`#5cc2cf`**（`style.css:120`） |
| `--c-ping-4` | `#2f8f7f` → **`#2e93a2`**（`style.css:37`） | `#5fc9b4` → **`#5cc2cf`**（`style.css:124`） |

**裁定依据两条：**

1. **代价极低**：一次改 4 个值，不新增 token、不动任何选择器，与主色改动同批提交即可。
2. **这是本次改动引入的副作用，应当由本次销毁。** 暗色档 ΔE **11.9** 已经贴到「读成同一色」的 10 这条线；
   而 `.chart .live-dot` 是**主色填充的实心点、就画在折线图上** —— 主色搬进 `--c-down` 的色相邻域之后，
   「下行折线被读成主色」是**必然产生的读数风险**，不是审美问题。

**落到套用顺序里**：已从 §7.1 的「（可选）」**移入必须做**（第 8 步）；§2.1 与 §5.2 的措辞也已同步为「本轮纳入」。
改完的复核方式见 §8.1 第 3 条（详情抽屉里并排看 `.live-dot` 与下行折线）。

### 8.3 本轮的额外产出（超出团队要求的部分）

- **发现并修复了一处既有 WCAG 失败**：`.seg` / `.bar` 的越线态与空槽只有 2.14:1（§5.1）。
  这不是主色改动引入的，是原方案的漏项 —— 原文档把 `.seg` 的机制列为「保留」，没有复算越线态的对比度。
- **发现 `--line` / `--line-2` 的 hover 反向陷阱**（§4.3）：把常驻边界提亮之后，5 处 `:hover` 会变成「悬停后变淡」。
  不加 `--line-control-hover` 就会踩这个坑，而且**看起来很像是「hover 样式没生效」**，不容易定位。
- **发现 `prefers-contrast: more` 档不覆盖 `--line-control`**（§4.4 的 B13/B14）：
  用户开了系统高对比度之后，控件边界会是 `#b9bdc3`（1.89:1），**比默认主题还弱** —— 与用户的选择正好相反。
- **确认 `--accent-fill` 与 `--accent-on-soft` 当前是零引用的死声明**（§1.2），所以合并零风险。
- **订正了一处会误导验收的数值错误**：本文档早先写的「玻璃叠草地」合成色 `#48633d` 是错的（逐通道合成应为 **`#48603d`**），
  由此算出的 4 个对比度也跟着偏了（4.98→**5.16** / 1.07→**1.11** / 3.69→**3.82** / 6.71→**6.96**）。
  已经全部订正，并补了一条**自带对账**：`#c0eb96` 压 `#48603d` = **5.16:1**，
  与 `theme/style.css:91` 里原本就写着的 `/* 4.76:1 / 5.16:1 联机中 */` **逐位吻合** ——
  这是两个独立来源对上，可以证明订正后的值是对的。
  **如果不订正，§7.3 ② 那条「合成色断言」会必然失败**，反而把「鸡场没变」这个正确结论判成事故。
- **把一项不可执行的验收判据换成了确定性判据**（本节新增，2026-09-29）：§7.3 ③ 原写
  「改前/改后 `.farm` 区域**像素差 = 0**」。鸡场是活场景（NPC 在走、相机在动、云在飘），
  两次截图的像素差**必然非 0** —— 这条判据会被噪声吃掉，**必然误报**，是「判据本身失效」而不是「改动有问题」。
  已换成 `.farm` 子树**计算样式 sha256 指纹**：A/B 同 DOM 对照、两侧同哈希、退出码 `0`，
  实测 **65** 个稳定元素、连跑 3 次跨 2 个实例同值。原「像素差」降级为**人眼旁证、不作判据、且按「必然非 0」预期看**。
- **顺手拆掉了一个判据自身的抽取陷阱**：把「带模板字面量的脚本里的表达式」按源码原文取出来直接用，
  会把 `\\s+` 送成 `/\\s+/`，元素键从 `span#room-state.conn.live` 变成 `span#room-state.conn live`，
  于是**指纹必然不同** → 假警报。取表达式必须按模板字面量语义还原。
  `docs/hud-top-probe.mjs --fp` 已按此实现并在注释里写明。
- **订正了两处「会漂的核对口径」**：§3.2 的「`grep` 命中 7 行 / 8 行 / 区块头 `:441`」与 §7.3 ① 的 `awk 'NR>=441'`
  —— 套用 delta 后行号与条数都漂了（区块头 → `:453`、引用点 11 处）。断言结论不变（窗口内仍为 0），
  但核对形式已改为**按区块头锚点取窗口、只判「窗口内计数 = 0」**：不写行号、不写条数，因此不会再漂。
- **明确了指纹判据的覆盖边界**：`#hud` 就在 `#farm` 里面，所以面板侧的计算样式**也在**指纹里。
  这不是误报而是**判据偏严**；若之后有意改面板侧（如第 9 步的 `.conn.live` 混色基底），
  指纹会照实变化，**应先重采基线并写清是有意改动**。
